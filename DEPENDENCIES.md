# Pinned source dependencies

The project keeps dependency recipes and lock data in Git, not upstream source trees. `flake.nix` declares source references; `flake.lock` records the resolved revisions and Nix content hashes. Nix fetches these trees into the store and assembles the vendor source root at `MESHTASTIC_VENDOR_ROOT` for CMake.

ESP-IDF registry components are separately listed in `registry-components.json` with archive SHA-256 hashes. Meshtastic firmware is pinned as a Nix source input, including the nested source repositories declared upstream. No Git submodule commands are needed for a fresh checkout.

## How the pinned versions are selected

The starting point is the `platformio.ini` and ESP-IDF component manifests in the exact Meshtastic firmware revision selected by this repository. For the ThinkNode M9, inspect the `thinknode_m9-tft` environment and follow its `extends` chain. That identifies the board, build flags, PlatformIO platform and framework versions, and declared library dependencies that define the firmware build being reproduced. Do this against the pinned source, not the current upstream branch, since those declarations can change over time.

PlatformIO is a source of build intent and dependency declarations; its package cache is not the source of the Nix lock file. Each firmware and library source used by the CMake target is declared as a Nix flake input in `flake.nix`. Git inputs use an explicit tag or commit, and `nix flake lock` records the resolved revision and Nix content hash in `flake.lock`. The ESP-IDF toolchain is selected through the `v5` development shell from `esp-idf-nix`; the project manifest narrows the framework requirement to `>=5.5.6,<5.6.0`.

ESP-IDF components follow a separate path. The local component manifest declares the required component names and version constraints. `dependencies.lock` records the ESP Component Manager resolution, while `registry-components.json` records the exact registry archive URLs, SHA-256 hashes, and component hashes fetched by Nix. Updating these pins means checking the declarations in the pinned firmware, resolving the intended versions, updating the Nix input or registry archive data, and rebuilding to confirm the selected sources still compile together. The lock files do not get generated by converting a PlatformIO lock file.

To inspect the firmware declarations in the source selected by the flake, enter the development shell and read the files under `MESHTASTIC_FW_ROOT`, for example `nix develop --command sh -c 'sed -n "1,240p" "$MESHTASTIC_FW_ROOT/platformio.ini"'`. Then inspect the M9 environment's inherited settings and its component manifests. Compare those declarations with `flake.nix`, `components/meshtastic/idf_component.yml`, `dependencies.lock`, and `registry-components.json`; the CMake source list in `components/meshtastic/CMakeLists.txt` shows which of the fetched libraries are actually compiled into this target.

To update a source, change its reference in `flake.nix`, regenerate `flake.lock`, build the firmware, and review the resulting revision and hash changes. Keep device-specific configuration and small compatibility overlays in this repository; do not commit fetched dependency trees or build outputs.
